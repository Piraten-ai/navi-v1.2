AADS NAVI - Complete Technical Reference Manual (Current)read old Version for insightVersion: 1.1 (draft)Last updated: 2026-01-25System: Arctic Autonomy Decision Support (AADS) - NAVIScope: Jetson backend + Raspberry Pi frontend/bridge + PC dev/training---1. System OverviewAADS NAVI is an offline-first maritime decision support system. The system is split across two devices plus a PC dev/training node:Jetson: backend, AI inference, sensor ingestion, data storageRaspberry Pi (realtime-pi): dashboard UI and Arduino analog-to-digital bridgeDevelopment and training run on this PC (full stack). The laptop connects to the PC for access and control.Core goals:No internet dependencyLow-latency local inferenceClear separation of responsibilitiesSimple deployment per device---2. Architecture and Data FlowHigh-level flow:Sensors and Arduino-> Raspberry Pi bridge (ADC, formatting)-> Jetson backend (FastAPI)-> WebSocket stream-> Raspberry Pi UI (dashboard)Key points:Jetson owns all AI modules and storageRaspberry Pi owns the UI and hardware bridge for analog signalsThe UI consumes REST + WebSocket from JetsonBridge payload format is defined in docs/current/BRIDGE_SPEC.md---3. Hardware TargetsJetson (backend):Runs FastAPI, AI modules, Ollama, databasesConnected to cameras, NMEA, Signal K, and local storageRaspberry Pi (frontend/bridge):Runs dashboard UIReads analog signals from Arduino and forwards to JetsonOptional local cache for offline UI resiliencePC (dev/training):Runs full stack for development and training data generationNo lightweight mode required---4. Software ComponentsBackend (Jetson):FastAPI API and WebSocketAI modules: Vakten, Navi, Navigator, Legen, Psykologen, IngeniorenData services: PostgreSQL, InfluxDB, Redis, MinIOModel hosting: OllamaFrontend (Raspberry Pi):UI technology: recommended Qt/QML (non-HTML), final choice pendingConnects to Jetson via REST and WebSocketDisplays status, alerts, instruments, map, and chatBridge (Raspberry Pi):Reads analog data from ArduinoNormalizes and sends to Jetson endpoints---5. Environments and ConfigRecommended config layout:config/backend.env.jetsonconfig/backend.env.devconfig/backend.env.sim (PC simulation)Backend should load a specific env file per deployment, not a generic .env.Use `BACKEND_ENV_FILE` with `docker-compose.dev.yml` to switch dev vs simulation.Frontend should use consistent VITE_* variables only.Dev uses PostgreSQL to match production behavior.Bridge spec:docs/current/BRIDGE_SPEC.md---6. Deployment OverviewJetson:Build and run backend stack with docker-compose.ymlEnsure AI models and sensor devices are availableRaspberry Pi:Run UI and bridge services with docker-compose.pi.ymlConfigure Jetson IP/hostnamePC Dev:Run full stack locally with docker-compose.dev.ymlUse dev env file with local servicesFor full simulation, run scripts/sim/run-pc-sim.ps1 or scripts/sim/run-pc-sim.sh---7. Current Gaps to Resolve (Tracked)Finalize UI technology on Raspberry Pi (React vs Qt/QML)Define camera simulation workflow for PC (Omniverse or other)---8. Debugging and Logs (Quick Guide)Backend:Health: `GET /health`Status: `GET /api/v1/status`Bridge latest: `GET /api/v1/bridge/analog`Logs: `docker compose logs -f backend` (Jetson or dev)Bridge:If serial is not found: verify `/dev/ttyACM0` exists and matches the Arduino deviceIf payloads are rejected: ensure all `signals` values are numericIf no UI panel: confirm WebSocket is connected and `type: "bridge"` arrivesInfluxDB:If bridge logs are missing, verify `INFLUXDB_TOKEN` matches the compose token---9.
